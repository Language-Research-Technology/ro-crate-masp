# Plan for sorting out this repository

This repository started as an experiment to adapt the "Schema.org Style Schema" (SOSS) approach to defining classes and properties as used by RO-Crate into a fully functional schema and profile language: RO-Crate MASP.

The repo contains the spec for MASP and a bunch of tools and examples.

All of this needs to be sorted out and moved into different repositories so that this repo gets pared back to being just the Core MASP spec (intro materials, and the MASP Profile for MASP itself) -> To ResearchObject.org (subject to governance at the RO-Crate steering committee level).

- **Validator** - has already moved to crateworks - needs to be removed from here and maintained there.
- **Tools** - all scripts, tools etc (doc generation, MASP generation from OWL etc) -> `ro-crate-masp-tools`. Will make a new repo here in language-research-technology; may move to the crateworks org later.
- **Examples** (under `schemas/` and `profiles/` here) will move to an `ro-crate-examples` repo which may also end up at researchobject.org.
- **Templates** - already live in [masp-templates](https://github.com/Language-Research-Technology/masp-templates); `schemas/template` here is superseded.

New repos start from a plain copy of the current files; git history is not carried over (it stays here).

We will do this a bit at a time, merging each step back to main, until just the core spec remains. Then we offer it to the RO-Crate team as an official part of RO-Crate. Rules for each step, so main is always usable if we stop partway:

- Only delete something here once its new home exists and works (tests pass, docs build).
- In the same change, add a pointer in the README saying where it went.
- Tick the step off in this file in the same change.

## Things to sort out before or during the move

1. **Spec needs tools to build its docs.** `profile-documentation.md` for the MASP profile is generated by `generate-masp-docs.js`. Once the tools move, this repo needs `ro-crate-masp-tools` as a dev dependency (npm or git) to rebuild them, or we commit the generated docs and rebuild them from the tools repo.
2. **Spec text describes the implementation.** `profiles/ro-crate-masp/profile-text.md` talks about "the validator" throughout and names `soss-validator.js`. Rewrite it as normative rules ("a conforming processor MUST..."), with no dependency on any particular code.
3. **Permanent identifiers and URLs.** The MASP profile `@id` is `https://language-research-technology.github.io/ro-crate-masp/profiles/ro-crate-masp/profile-crate/`, and the examples (and maybe real LDAC data) point at GitHub Pages URLs here via `conformsTo`. The MASP profile will get a w3id identifier: choose the path (e.g. under `w3id.org/ro/`, alongside RO-Crate's `w3id.org/ro/crate`, which needs RO-Crate team agreement), submit the redirect PR to w3id, then change the profile `@id` and the `conformsTo` references in the examples to use it. Keep the old Pages URLs working (redirects or a frozen copy).
4. **Validator parity.** In progress: [crate-works/ro-crate-masp-validator#1](https://github.com/crate-works/ro-crate-masp-validator/pull/1) ports everything below except the npm, register-rules and extra-test items. The validator is at [crate-works/ro-crate-masp-validator](https://github.com/crate-works/ro-crate-masp-validator), extracted from commit `e3e995c` (2026-10-13). Checked 2026-11-18 - it is behind this repo:
   - `lib/masp-validator.js` here has changes made since: `http://schema.org/` IRIs instead of `https://`, `rdfs:Literal` as a range (needed for the OWL-converted schemas), and `schema:URL` value checking (`isValidUrl`). Port these.
   - Its test fixtures in `test-data/` are copies of profiles from here and predate the `http://schema.org/` change; refresh them along with the port.
   - The cyclic-reference fix (PR #33 / #32) is not in it either.
   - It is `"private": true` and not on npm. [PR #2](https://github.com/crate-works/ro-crate-masp-validator/pull/2) sets it up to publish as `@crate-works/ro-crate-masp-validator`; tools and examples will depend on that.
   - `lib/register-rules.js` (used by `generate-masp-docs.js`) is not in the validator repo - it goes to tools.
   - Tests only here that touch the validator: `ldac-dmlex-profile.test.js`, `schema-org-schema.test.js` - decide whether they belong in the validator or tools repo. The rest (mode files, owl-to-masp, rocxl, register-rules) go to tools.
5. **Test fixtures.** The tools tests load crates from `profiles/` and `test_data/`. The tools repo needs its own copies so it does not depend on the examples repo (which depends on the tools to build).
6. **Template check.** Compared `schemas/template` with masp-templates: masp-templates builds its crate from `additional-ro-crate-metadata.xlsx` (its committed `ro-crate-metadata.json` is just `{}`), and its `schema-text.md` is newer. Only here: the generated `crate-o-mode.json`, `index.html`, `ro-crate-preview.html` and `schema-documentation.md`. Nothing obviously worth keeping, but confirm whether masp-templates should ship a Crate-O mode file.
7. **Licence.** Repo is Apache-2.0. Check what licence researchobject.org uses for spec text (likely CC-BY) before handing over.
